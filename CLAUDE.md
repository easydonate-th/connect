# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Turborepo is 2.11.7, which may differ from training data. Before changing `turbo.json` or Turborepo commands, read `node_modules/turbo/docs/README.md` and the relevant pages under `node_modules/turbo/docs/`. `turbo.json` sets `agentGuidance: false`, so turbo does not generate an `AGENTS.md`.

## Overview

EasyDonate Connect: a desktop companion app that connects to an EasyDonate alert widget over WebSocket and forwards donation events to VRChat via OSC/MIDI and to VTube Studio, which throws an item at the model.

Bun monorepo managed with Turborepo (`bun@1.4.3`, workspaces `apps/*` and `packages/*`):

- `apps/desktop` (`@ezdn/desktop`) — Electrobun desktop app (Bun main process + React 19 webview) for Windows x64, macOS arm64 and Linux x64.
- `apps/unity` — Unity/VRChat world project. The `unity-vrc-udon-sharp` and `unity-vrc-world-sdk-3` skills (`.claude/skills/`) cover its UdonSharp scripts and scene setup. Only the `app.easydonate.sdk` VPM package (`Packages/`) is tracked (see `apps/unity/.gitignore`). Its example prefabs live inside it in `Examples/`, with their own `EasyDonate.SDK.Examples` asmdef and U# assembly asset, so both VCC and the `.unitypackage` ship them; `legacyFolders` in its `package.json` makes VCC delete `Assets/EasyDonateSDK`, where SDK 1.0.0's separate examples package put them. `vpm/` holds the VPM listing: `source.json` and a Scriban-templated `Website/`, which the `listing` job of `.github/workflows/release.yml` renders with `vrchat-community/package-list-action` after each release and deploys to GitHub Pages (`https://easydonate-th.github.io/connect/index.json`). VCC downloads release zips without auth, so the listing only works while the repo is public.
- `packages/` — not created yet (the workspace glob is reserved).
- `docs/` — user-facing setup guides per integration (VRChat, VTube Studio, Warudo WIP), linked from `README.md`.

## Commands

Root (run from repo root):

- `bun install` — install deps (`prepare` installs lefthook. If JS, TS, JSON or CSS files are staged, its pre-commit job runs `bun run fix` and stages the fixes again.)
- `bun run dev` — `turbo run dev` across workspaces.
- `bun run build` — `turbo run build`.
- `bun run lint` — `oxlint .`
- `bun run fmt` — `oxfmt .`
- `bun run fix` (`ultracite fix`) / `bunx ultracite check` — format + lint via Ultracite preset. `oxfmt.config.ts` ignores `.claude/**` so third-party skill docs are never reformatted.
- `.claude/settings.json` has a `PostToolUse` hook that runs `bun run fix` after every Write or Edit. The hook formats the file before Claude reads it back. Do not run `fix` by hand after an edit. The hook does not touch Markdown.

`apps/desktop`:

- `bun run dev` — `electrobun prepare` + `vite build` + `electrobun dev --watch` (rebuilds bundled view on change).
- `bun run hmr` — runs only the Vite dev server on port 5173; start the app with `bun run start` in another terminal, and the main process (dev channel) detects the server and loads the webview from `http://localhost:5173` for HMR.
- `bun run start` — same as `dev` without `--watch`.
- `bun run build` / `bun run build:canary` — production builds (`--env=stable` / `--env=canary`).

Release: bump `app.version` in `apps/desktop/electrobun.config.ts` and/or `version` in `apps/unity/Packages/app.easydonate.sdk/package.json`, merge to `main`, then run `gh workflow run release.yml`.

- It makes a release tagged and titled `Release-<DDMMYYYY>-<N>` (Asia/Bangkok date; `N` is one more than the highest count that day, where an old tag without a count counts as 1; runs queue so two can't take the same tag) whose notes list both versions and link each desktop installer by its release download URL, with the desktop installers (`win-x64-…-Setup.zip`, `macos-arm64-….dmg` and `linux-x64-…-Setup.tar.gz`, each built on its own runner by the `desktop` job's matrix, since Electrobun builds only for its host; the macOS job sets `ELECTROBUN_DEVELOPER_ID` to `-`, which turns on `build.mac.codesign` and makes Electrobun sign the app ad hoc, since there is no Apple Developer ID; macOS calls an unsigned download damaged, but offers Open Anyway in Privacy & Security for an ad-hoc one) and the SDK `.unitypackage` (checkout uses LFS for the examples' audio and font).
- The updater's files go to the bucket only: `stable-<os>-<arch>-update.json`, the `.tar.zst` bundle and the `.patch` that the build makes from the previous release's bundle, which it fetches from `release.baseUrl`.
- The SDK package zip is attached only if no earlier release has that SDK version, because the listing job adds every release zip with a root `package.json` (the desktop installers have none) and would otherwise list the version twice; the `listing` job then rebuilds the VPM listing and redeploys Pages.
- `release.baseUrl` is `https://nozomi.easydonate.app/connect`, the `connect` bucket of a MinIO server behind Cloudflare. The app reads it anonymously by path. The `release` job creates the release as a draft and then uploads the updater's files to the bucket with the AWS CLI. It uploads the `.patch` files first, then the `.tar.zst` bundles, then `update.json`, so a manifest never names a missing file. The upload uses the `S3_ACCESS_KEY` and `S3_SECRET_KEY` secrets, path-style addressing and `Cache-Control: no-cache`. The job skips the upload for a prerelease, so the app updates from non-prereleases only. Then it publishes the release. The bucket keeps every patch, so an app several releases behind can patch its way up.
- Apps 1.6.0 to 1.6.2 use `https://github.com/easydonate-th/connect/releases/latest/download` as `baseUrl`. `Release-14102026-1` (1.7.0) is the last release that carries `update.json` and the bundle, so those apps update only while it is the latest release. After a newer release, they find no update, and their users must install the new version by hand. Apps up to 1.5.0 have no `baseUrl` and read the desktop version from the `- EasyDonate Connect: <version>` line of the latest non-prerelease's notes, so keep that line's format if you change the notes.

There is no test runner or test suite yet (oxlint config includes the vitest preset in anticipation).

## Desktop app architecture

- **Electrobun, not Electron.** Main process runs on Bun (`mainProcess: 'bun'`) with entrypoint `src/bun/index.ts` (see `electrobun.config.ts`). `electrobun prepare` generates `.hutch/devkit` (gitignored); `vite.config.ts` pulls Electrobun aliases from it and `tsconfig.json` maps `electrobun/*` imports into it via `paths` (it does not extend the devkit tsconfig, whose `baseUrl` TS 7 rejects). Run `prepare` (any dev/build script does) before type-checking or building in a fresh checkout. Type-check with `../../node_modules/.bin/tsc --noEmit -p .` from `apps/desktop`.
- **Three source dirs:**
  - `src/bun/` — main process. `index.ts` creates the `BrowserWindow` and menu, unless `mutex.ts` finds another instance on the same channel (a kernel32 named mutex on Windows, a `flock` on a file in `userData` through libc on macOS and Linux; a second instance would forward every donation twice), in which case it shows a message box and quits; `icon.ts` sets the window icon from `Resources/app.ico` (copied from `build.win.icon`) with user32 `WM_SETICON`, since Electrobun never sets it on Windows; `autoplay.ts` (`allowAutoplay`, called before the window opens) appends `--autoplay-policy=no-user-gesture-required` to `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` with kernel32 `SetEnvironmentVariableW` on Windows, since WebView2 keeps sound off until the user clicks the page and hit sounds must play after an auto connect (WebView2 appends the variable to Electrobun's own arguments, and macOS and Linux webviews need no click), and `rpc.ts` implements the RPC handlers (`openDataFolder` and `openLogsFolder` open `userData` and the log folder with `Utils.openPath`, and `openExternal` opens a URL in the default browser); `config.ts` caches the config in memory and persists it atomically to `Utils.paths.userData/config.json`; `language.ts` does the same for the UI language in `language.json` and falls back to English when the file is missing. The language is not part of `Config`, so a stale webview `saveConfig` cannot overwrite a switch. Its `getMessages` translates the already-running message box and the menu, which `index.ts` rebuilds after a switch; `libs/update.ts` reads the app version (`Updater.localInfo.version()`), checks with Electrobun's `Updater` (which compares bundle hashes, so `checkForUpdate` also requires a newer version with `Bun.semver.order`), and `installUpdate` downloads the update and relaunches into it (the `Updater` reports failures through `updateInfo().error` and its status history rather than throwing, and is disabled on the dev channel); it logs the `Updater`'s status changes and sends the install stages (a key of the `settings.updateStages` messages, plus a percent while the full bundle downloads; a patch download reports none) to the webview as `updateStage` through the sink `index.ts` sets with `setUpdateStageSink`; `libs/forward.ts` calls each enabled output that `src/shared/platform.ts` (`isOutputSupported`) says runs on `process.platform` (MIDI runs on Windows only; OSC and VTube Studio everywhere); `libs/vrc/` holds the VRChat outputs (`osc.ts`; `midi/`) and `libs/vts/` the VTube Studio one. In `libs/vrc/midi/`, `index.ts` (`sendDonationMIDI`) sends a donation in paced chunks, one donation at a time (VRChat's MIDI input throws and drops events when a frame gets more than 128); `utils.ts` documents the protocol and `encodeDonation` turns a donation into Control Change messages (JSON, one character each); `winmm.ts` has `getMIDIDevices` and `sendMIDI`, which call winmm.dll through `bun:ffi` (Windows only; ports come from loopMIDI).
  - `src/mainview/` — React 19 + Tailwind v4 + shadcn/ui webview. Vite root is `src/mainview`, output goes to `apps/desktop/dist`, which Electrobun copies into `views/mainview/` (loaded as `views://mainview/index.html` in non-HMR mode). Import alias `~/*` maps to `src/mainview/*`.
  - `src/shared/` — imported by both sides with relative paths: the zod `ConfigSchema` and the types derived from it (`config.ts`, built with `zod/mini`, whose checks are functions such as `z.minimum` and `z.pipe(…, z.transform(…))`, because classic zod's methods put about 65 KB of zod in each bundle; every field has its own fallback through `withFallback` (zod's `.catch`, read as the member `z.catch` and aliased so the promise lint rule doesn't misfire; destructuring `z` would keep every zod export, locales and JSON Schema included, in both bundles), so `ConfigSchema.parse` heals one bad value in `config.json` or an RPC payload without resetting the rest, drops unknown fields, drops invalid array entries such as custom images or sounds whose `fileName` isn't in their import's `<8 hex>.<ext>` format (earlier versions' `ezdn-` prefix is allowed, and a sound may end in `mp3`, or in `wav` or `ogg` from 1.8.0), puts back `punch` for a `hitSound` that names neither a preset nor one of the `customSounds`, and sorts and prunes throw rules, adding a default one when none are left; the main process runs it at its I/O boundary in `bun/config.ts`; `validateConfig` reuses the field schemas to report, rather than heal, each invalid field of the UI's draft, plus the rules that span fields, as messages keyed by form path), the `Donation` type (`donation.ts`) and the widget socket's URL and state (`widget.ts`), plus the `AppRPC` contract (`rpc.ts`) and the UI text (`i18n/`). In `i18n/`, `index.ts` combines one namespace file per area from `messages/`: `app` (shared UI text, the menu, form validation and `errors`), `widget`, `vrc`, `vts` (`throw`, `hitSound`, `rules`), `warudo` and `settings`. Each file has an `en` object and a `th` object typed `typeof en`, so TypeScript reports a missing or extra key. A value with parameters is a function. When the main process throws an error that the user sees, it throws a `TranslatableError` from `i18n/error.ts`. Its message encodes a key of the `app.errors` messages and the parameters, because Electrobun sends only an error's message across RPC. `describeError` and `describeMessage` render that message in a given language, English by default, so a toast shows the user's language and the log stays English. An image import rejection carries such a message as its `reason`.
- **VTube Studio output:** in `src/bun/libs/vts/`, `client.ts` (`withVTSSession`) opens a Plugin API WebSocket (Bun's global `WebSocket`) per call, authenticates and closes it; `api.ts` types each request's `data` and response by `messageType`. The plugin token lives in `token.ts`'s `Utils.paths.userData/vts-token.json`, not in `Config`, so a stale webview `saveConfig` can't overwrite it; without a valid token, `AuthenticationTokenRequest` waits up to two minutes for the user to click Allow in VTube Studio, and concurrent sessions share that one request (`allowCustomImages` does the same for the `LoadCustomImagesAsItems` permission). `throw.ts` (`sendDonationVTS`) finds the throw rule with the highest `minAmount` the donation reaches (none: it throws nothing) and throws its `count` items, each picked at random from the selected `Items` folder files and all of the user's images, or, when the rule is `custom`, from its own `items` and `images`, 150 ms apart in one session, in batches of 20 (a rule allows up to 50, and VTube Studio fits about 60 items), each of which starts after the last one's items unloaded: it loads the item off-screen with `unloadWhenPluginDisconnects`, flies it with `ItemMoveRequest`, from one of the screen edges the zone's `zoneDirections` entry lists (left, right or both, picked at random), at one of the rule's `zones` (head, body, feet) picked at random, as wide as the zone's `zoneWidths` entry (pixels, centered on the model's x) and a band of the model's visible height that `outline.ts` (`getModelBounds`) reads from one `ModelOutlineEvent` frame (the session's `waitForEvent` resolves on the next event of a name; without a frame it aims at `CurrentModelRequest`'s model position), moved down by the rule's `zoneOffsets` for that zone (pixels, negative moves up, converted with the frame's `windowSize`, since item x and y span -1 to 1 over the window; without a frame, width and offset don't apply), knocks the model's head away from it with `reaction.ts` (`createHitReaction`: a damped spring, shared by the donation's items, that adds to the `FaceAngleX/Y/Z` and `FacePositionX` tracking inputs through `InjectParameterDataRequest` in `add` mode every 33 ms until it settles, scaled by `hitForce`, 0 for off, and less for body and feet hits; the session stays open until it does), plays the hit sound (`hit-sound.ts` (`playHitSound`) sends the config's `hitSound` and `hitVolume` to the webview as the `hitSound` message through the sink `index.ts` sets with `setHitSoundSink`, because the Plugin API has no request that plays audio), drops it out of view and unloads it (sending `ItemUnloadRequest` at the hit when `fadeTime` is set, so it fades while dropping, else after the drop), then closes the session. It sends a custom image's data only on its first load, then reuses the name VTube Studio returned until a load fails with 751 (VTube Studio restarted). `images.ts` imports images through `importUserFiles` in `user-files.ts`, which opens `Utils.openFileDialog`, checks each file against VTube Studio's custom data limits (PNG/JPG/GIF header, under 5 MB, 64-2048 px a side) and writes it with `writeUserFile` to `Utils.paths.userData/vts-images` as `<8 hex>.<ext>`. VTube Studio requires a custom image's name to be 8-32 letters, digits or hyphens with the extension, and that name fits. `sounds.ts` (`saveVTSSound`) writes an MP3 that the webview made to `vts-sounds` the same way, after it checks for an MP3 header. The `saveConfig` handler deletes images and sounds the saved config no longer lists. The main window enables Electrobun's `appdata://` protocol (`allowedProtocols.appData`), which serves `userData` to the webview, so `VTS/ImageThumbnail` previews images through `getVTSImageUrl`; it also exposes `config.json` and `vts-token.json` to whatever the window loads, so it must never navigate to remote pages. `connection.ts` (`testVTSConnection`) reports the VTube Studio version and loaded model for the Test connection button; `items.ts` (`getVTSItems`) lists the `Items` folder; VTube Studio reads the folder from disk for this, so the UI only scans on demand.
- **Typed RPC bridge:** `src/shared/rpc.ts` defines `AppRPC`: the `bun` side answers `getConfig`/`saveConfig`/`getLanguage`/`setLanguage`/`getMIDIDevices`/`getVTSItems`/`testVTSConnection`/`importVTSImages`/`saveVTSSound`/`readVTSSound`/`openDataFolder`/`openLogsFolder`/`getAppVersion`/`getPlatform`/`checkForUpdate`/`installUpdate`/`openExternal`/`getWidgetState`/`connectWidget`/`disconnectWidget` (the VTube Studio, import, sound and update wrappers raise `maxRequestTime` to cover the VTube Studio approval wait, the open file dialog, the transfer of a long sound's base64, the updater's 30-second wait for `update.json` and the download) and receives the fire-and-forget `testDonation` and `log` messages (a test donation carries the form's draft config, which the handler heals with `ConfigSchema`); the webview receives `log`, `updateStage` (stored in `libs/update-stage.ts`, read with `hooks/use-update-stage.ts`), `hitSound`, and the widget socket's `widgetState`, `rawFrame` and `donation`. `playHitSound` in `libs/hit-sound.ts` plays a random take of the preset from `src/mainview/sounds/` (Kenney's CC0 Impact Sounds as mono VBR V2 MP3 made with LAME, decoded the way the user's MP3 sounds are). It loads the takes with `import.meta.glob` and decodes them with Web Audio, because `<audio>` can fail to stream from the `views://` scheme on macOS. It also plays one of the user's sounds by `fileName`. It keeps the presets decoded, but only the last user sound it played, since a user sound has no length limit. It reads that file as base64 through the `readVTSSound` request, since a `fetch` from `appdata://` would be cross-origin. `libs/rpc.ts` passes the request to `setSoundReader`, because `hit-sound.ts` importing `libs/rpc.ts` would make an import cycle. If the audio output does not start within a second, it drops the sound and logs a warning once. That happens only while a webview waits for a click. The user adds sounds through a hidden file input in `VTS/HitSound`, so the webview reads each file itself and a large file never crosses RPC. `hooks/use-vts-sound-import.ts` converts each picked file with `convertToMP3` from `libs/sound-convert.ts` and sends the MP3 as base64 to `saveVTSSound`. `convertToMP3` decodes the file with an `OfflineAudioContext` at 44.1 kHz. It reads any audio or video file the webview can decode, and WKWebView rejects MOV and WMA. It mixes more than two channels down to stereo and encodes a VBR V2 MP3 with LAME from `wasm-media-encoders`. It yields to the UI after each second of audio, so a long file does not freeze the window. It fetches `mp3.wasm` and passes the bytes to the library, because the library would stream a URL, and streaming needs the `application/wasm` type from `views://`. There is no size or length limit. The main process implements the handlers in `src/bun/rpc.ts`; webview wrappers live in `src/mainview/libs/rpc.ts`. To add a capability: extend `AppRPC`, implement the handler in `src/bun/rpc.ts`, add a wrapper in `libs/rpc.ts`.
- **Donation flow:** the main process owns the widget socket, because only a native client can set request headers. `src/bun/libs/widget/socket.ts` connects with Bun's `WebSocket` to `wss://socket.easydonate.app/ezdn<widget query>&ex=easyconnect`, without the widget link's `ts` parameter. It sends `User-Agent: EasyDonate Connect/<app version> (<Windows|macOS|Linux>; <arch>)`, which Cloudflare's analytics show. Cloudflare in front of the socket answers a request without a User-Agent (Bun sends none by default) with a 403 challenge, which the client reports as close code 1002. `getSocketUrl` in `src/shared/widget.ts` builds the URL, and the webview calls it too to flag an invalid URL. The tsconfig's DOM lib hides the Bun constructor that takes options, so the file casts `WebSocket` once.
  - The socket reconnects forever with backoff and jitter. Only `close` schedules a reconnect, because a failed connect fires `error` and then `close`. After 30 seconds without a message it sends `{"event":"ping"}`, and after 60 it reconnects. It ignores events from a socket it already dropped. `connectWidget` with the URL already in use keeps the connection, so a reloaded webview that auto connects does not drop it.
  - `toRawLogFrame` (`raw-frame.ts`) prepares each frame for the webview's raw log. Some frames (e.g. PONG) arrive JSON-encoded twice, and `socket-frame.ts` unwraps them. `parseDonationMessage` (`donation.ts`) turns a `DONATE` frame into a `Donation` without validating fields, since the widget's message shape is fixed. The socket sends the donation to the webview and to `forwardDonation`, which logs it and calls the enabled OSC/MIDI/VTube Studio outputs with the cached config. A test donation goes to `forwardDonation` with the form's current values (`getValues`) instead, so it tests unsaved changes too.
  - The socket pushes its `WidgetState` (status and socket URL) to the webview on every change. `libs/widget-state.ts` mirrors it and the last donation. `hooks/use-widget-connection.ts` reads them, asks for the state on mount, and sends Connect and Disconnect. The socket connects when the user clicks Connect, or on launch when the saved `autoConnect` setting is on.
- **Logs:** `src/bun/logger.ts` writes to the console and to the session's log file, and pushes each entry to the webview over the `log` RPC message; the webview adds its own entries through `log` in `src/mainview/libs/logs.ts` (an in-memory store, read with `hooks/use-logs.ts`, that also records incoming socket frames (minus PONG heartbeats and TTS fields, which the main process strips, see `src/bun/libs/widget/raw-frame.ts`) in a separate 500-line buffer for the panel's Raw log toggle) and sends them to the main process as the bun side's `log` message, through the forwarder `libs/rpc.ts` sets with `setLogForwarder`, so the file gets them too. Raw frames never reach the file, because they carry donor names and messages. The Logs button toggles `components/LogsPanel.tsx`, whose text and the Logs button stay English like the log lines; its Folder button opens the log folder through `openLogsFolder`.
  - `src/bun/log-file.ts` keeps the files in `logs/` under `Utils.paths.userLogs` (`~/Library/Logs/<identifier>/<channel>` on macOS, `$XDG_STATE_HOME` on Linux; on Windows `userLogs` is the same folder as `userData` and the installed app, hence the subfolder). `startLogFiles`, which `index.ts` calls only after it holds the single-instance lock, so a second launch never takes a slot, creates `app-<ISO time>.log` for the session and deletes all but the newest three. It also prepends an `uncaughtException` listener, because Electrobun's own listener exits the process, and adds an `unhandledRejection` one. Lines are `ISO-time LEVEL message`, written with `appendFileSync`, so a crash loses none.
  - `installer.log` outlives the sessions. `libs/update.ts` writes each `Updater` status to it (download progress every 10%), the errors of `installUpdate`, and, through `logLaunch` at startup, the version, channel and hash that started. Electrobun's native helper replaces the app after the process exits and writes its result to a file that the next launch's `Updater` reports as a `complete` or `error` status, so that status and the launch line are the only record of an install. `startLogFiles` keeps the last 512 KB once the file passes 1 MB.
- **UI:** shadcn/ui (`components.json`, Radix base, Nova preset). Add components with `bunx shadcn@latest add <name>` from `apps/desktop`. Generated files in `components/ui/` are excluded from oxlint. `dialog.tsx` and `spinner.tsx` read their "Close" and "Loading" text with `useMessages()`, and `sonner.tsx` passes the translated `containerAriaLabel`. If you re-add one of these components with shadcn, put its translation back, because the generated file has English text.
  - `App.tsx` suspends on the initial config load (`use(initialConfigPromise)` plus `Suspense` in `main.tsx`) and passes it to `hooks/use-config-form.ts`, whose react-hook-form form holds the editable draft and is provided with `FormProvider`; components read and write it through the form context (`useController`, `useWatch`, `useFieldArray` for the throw rules, `setValue` with `shouldDirty`), and `NumberField` and `OutputCard`'s `name` cover number fields and output switches. Its resolver turns `validateConfig` into `formState.errors`, and because RHF revalidates only the changed field while most rules span fields, a `subscribe` effect revalidates the whole form on every change; `save` resets the form to what the main process stored. The `desktop-component-pattern` skill (`.claude/skills/`) sets the layout of a component's body and these form conventions.
  - `hooks/use-midi-devices.ts` lists MIDI ports over RPC, scanned on mount and on demand; `hooks/use-vts-items.ts` lists VTube Studio items only on demand, since the first scan shows VTube Studio's approval popup; `hooks/use-vts-image-import.ts` imports the user's images, which `VTS/Throw` adds to the draft; `hooks/use-unsaved-changes-toast.tsx` keeps a non-dismissible toast with a Save button and a Revert button (`reset()`, back to the saved config) on screen while the draft differs from the saved config, except while a component calls `useHideUnsavedChangesToast(true)` (`VTS/RuleItemsDialog` and `VTS/RuleZonesDialog` while open, since each one's Save button saves through `useConfigSave` from `hooks/use-config-form.ts` and then closes it; they ignore clicks outside; `VTS/ThrowRules` keeps the last rule dialog mounted after it closes, so Radix can play its exit animation).
  - `App.tsx` composes:
    - `WidgetConnection` (widget URL, auto connect, Connect/Test buttons)
    - `Integrations` (it reads the main process's platform with `use(platformPromise)` from `libs/platform.ts` and passes `isSupported` from `isOutputSupported` to an output, whose `OutputCard` then shows a "Platform not supported" badge in place of its switch and fields; accordion of `VRC/OSC` and `VRC/MIDI` under VRChat and `VTS/Throw` under VTube Studio, whose items are split into a VTube Studio tab (checkbox list from Scan) and a Your images tab, then the motion fields and `VTS/HitSound` (the Hit sound select, whose Your sounds group lists the user's sounds, each with a remove button beside its item, an Add sounds button, then Volume (%) and a Preview button that plays it in the webview), followed by `VTS/ThrowRules` (the Logic list of rules: Min THB, Items to throw, a Custom image checkbox whose Choose button opens `VTS/RuleItemsDialog` to pick from both tabs, a Hit zone button that opens `VTS/RuleZonesDialog`, which also holds each zone's throw sides (`VTS/ZoneDirectionField`, Left and Right checkboxes), pixel offset and pixel width, grayed out while the zone is unchecked (`validateConfig` skips them then), and a Reset button that, after a confirm popover, puts the rule's zone settings back to `createVTSThrowRule`'s defaults in the draft, and remove, each row a `VTS/ThrowRule`; `ConfigSchema` sorts them by Min THB and prunes picks no longer in the tabs), each wrapped in `OutputCard`; its `AccordionContent` gets `h-auto`, because the generated component fixes the content's height to what Radix measured on open and would clip content that grows later)
    - `Settings` (the Language select, the app version, the Data folder button, a GitHub button and Check for updates, then Update and restart, through `hooks/use-app-update.tsx`, which also checks once on launch, toasting only when an update is found and logging a failure as a warning, and toasts the result (the install toast's description is `UpdateProgress`, the stage label and a shadcn `Progress` bar) and refuses to install while the draft has unsaved changes, since the restart would drop them; links go through `openExternal` in `libs/rpc.ts`, never `<a href>`, since the window must not navigate to remote pages)
    - `LogsPanel`
    - a footer that credits Kenney for the hit sounds (`README.md` credits them too, and Kenney's license sits beside the files)
  - `TestDonationButton` (in `WidgetConnection`, `VTS/ThrowRules` and `VTS/RuleZonesDialog`) sends a fake donation through the `testDonation` RPC message and is disabled while the socket is connected or connecting.
  - The UI is in English and Thai. `libs/i18n.ts` holds the current language and sets `<html lang>` to it. Its `languagePromise` loads the stored language before `App`'s first render. Its `changeLanguage` switches the UI at once, then stores the choice with `setLanguage`. Components read text with `useMessages()` (`hooks/use-messages.ts`), and code outside React calls `getMessages()` when it runs. `validateConfig` takes the messages, and `useConfigForm` revalidates on a switch, so field errors change language. Log lines stay English. The `desktop-component-pattern` skill has the conventions.
  - Light theme only. The root font size is 18px (`font-size: 112.5%` in `index.css`), and every size in the UI is in rem, so text, controls and gaps grow with it. Sonner sizes its toasts in px, so `components/ui/sonner.tsx` sets its `--width` and `index.css` sets its padding, gap and font size in rem.
  - The font is FCVision, the EasyDonate site's font, bundled as woff2 in `src/mainview/fonts/` (only the weights the UI uses: 400, 500, 600). The files' ascent metrics (`hhea` ascent, `OS/2` typo and win ascent) are lowered from 1120 to 880 with fonttools, so the line box centers the 700-unit capitals beside icons, as Geist did; the macOS WebKit view ignores CSS `ascent-override`, so the files carry the change. Patch any newly added weight the same way, and do not add `ascent-override` in CSS, which would lower Chromium's ascent twice.
